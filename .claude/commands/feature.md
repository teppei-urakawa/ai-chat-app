## Phase 1: 設計（コードを書く前に必ずここを完成させる）

以下の項目を **テキストで回答** してから実装に進むこと。

### 1-1. 責務の定義
この機能が担う責務を **一文** で表す。

### 1-2. インターフェース設計
```
入力:  （型・形式・バリデーション条件）
出力:  （型・形式・エラー時の挙動）
副作用: （DB書き込み / API呼び出し / キャッシュ更新 など）
```

### 1-3. エラーケースの全列挙
起こりうる失敗パターンをすべて書く。「思いつかない」は不可。

- 外部依存の失敗（DB接続エラー, API タイムアウト）
- 権限・認証エラー
- 競合・重複

### 1-4. 依存関係マップ

### 1-5. テスト容易性の確認

## Phase 2: 実装

Phase 1 の設計に基づいて実装する。

### 実装の掟（違反したら Phase 5 のレビューで必ず落とす）
1. **`any` 禁止** — 型は必ず明示する
2. **単一責務** — 1関数1役割。複数のことをしている関数は分割する
3. **早期リターン** — ガード節でエラー処理を先に書く
4. **依存の注入** — DBやAPIは引数か env 経由で受け取る（ハードコード禁止）
5. **コメントは「なぜ」** — 「何をするか」はコードを読めばわかる

実装したら `npx tsc --noEmit` を実行し、型エラーがないことを確認する。

## Phase 3: ハーネス設計（テストを書く前に設計する）

### 3-1. テスト対象の関数・モジュールを列挙する

### 3-2. テストケース表（実装前に必ず作る）

| # | テストケース名 | 入力 | 期待する結果 | 種別 |
|---|-------------|------|------------|------|
| 1 | 正常系: ... | ... | ... | happy path |
| 2 | 異常系: ... | ... | エラーを返す | error case |
| 3 | 境界値: ... | ... | ... | edge case |

**種別の必須要件:**
- happy path（正常系）: 最低1件
- error case（異常系）: Phase 1-3 で列挙したエラーケースを全て網羅
- edge case（境界値）: 空・null・最大値・最小値を含む

### 3-2. モック設計

```typescript
// 使用するモックの型と戻り値を定義する
vi.mock('@/lib/db', () => ({ ... }))
```

## Phase 4: テスト実装と初回実行

1. `__tests__/` ディレクトリにテストファイルを作成する
2. Phase 3 のテストケース表を **すべて** 実装する
3. `npm test` を実行する
4. 結果を確認する（成功・失敗どちらでも Phase 5 へ進む）

---

## Phase 5: 自動レビューループ（全項目が ✅ になるまで繰り返す）

以下のチェックリストを評価し、❌ があれば修正して再実行する。
**最大5回** 繰り返す。5回で解決しない場合は詰まっている理由を報告する。

### チェックリスト
- [ ] `npx tsc --noEmit` でエラーがゼロ
- [ ] `npm test` で全テストが **PASS**
- [ ] Phase 1-3 で列挙した **全エラーケース** がテストで網羅されている
- [ ] `any` が実装コードに存在しない（`grep -r "any" 対象ファイル`）
- [ ] 実装が Phase 1 の設計（インターフェース・副作用・エラー処理）と一致している
- [ ] 既存の他のテストが壊れていない（`npm test` 全体が PASS）

### 失敗時の診断手順
1. エラーメッセージを **一字一句** 読む
2. 「症状」ではなく「根本原因」を特定する
3. 修正する（当て推量で直さない）
4. 修正内容を一行で説明する
5. 再実行する
